# 中转站（Relay）详解

大肥鱼中转站是一个**零依赖、单文件**的模型网关，解决一个很具体的问题：

> 大模型 API 太容易挂 —— 限流、欠费、封号、网络抖动。
> 如果机器人直连某一家，那家一挂，机器人就哑了。

它对外只暴露**一个固定模型名**，内部维护一条**可手动排序的降级链**。

---

## 为什么需要它

### 没有中转站的时候

```
AstrBot ──直连──→ 供应商A
                   ↑ 欠费了 → 机器人挂了
                   ↑ 要换 B → 改 AstrBot 配置 → 重启
                   ↑ 再换 C → 再改再重启
```

每换一次供应商，就要动一次机器人配置、重启一次，还容易填错。

### 有了中转站

```
AstrBot ──→ 中转站（对外固定叫 "dafeiyu"）
                ├─ 供应商A ← 欠费，自动跳过
                ├─ 供应商B ← 正在用
                └─ 供应商C ← 备用
```

换供应商 = 网页上拖一下顺序。AstrBot 那边**一个字都不用改**。

## 核心机制

### 1. 协议互转

上游 API 分两大流派：

| 流派 | 请求格式 | 典型代表 |
|---|---|---|
| **OpenAI** | `/v1/chat/completions`，`messages[]` | DeepSeek、Moonshot、大多数中转站 |
| **Anthropic** | `/v1/messages`，`system` 独立字段 | Claude 官方、部分第三方 |

中转站**对外统一说 OpenAI 话**，内部按供应商配置自动转：

```jsonc
{ "api": "openai" }     // 直接转发
{ "api": "anthropic" }  // 转换请求体 / 响应体 / 流式 SSE 事件
```

转换涵盖：
- `system` 提示词的位置（Anthropic 是顶层字段，OpenAI 是 messages 里的一条）
- `max_tokens` 的必填性
- 流式事件类型（Anthropic 的 `content_block_delta` ↔ OpenAI 的 `choices[].delta`）
- 结束原因（`stop_reason` ↔ `finish_reason`）
- Token 用量字段名

### 2. 鉴权风格

大多数 Anthropic 兼容站认 `x-api-key` 头，但**也有只认 `Authorization: Bearer` 的**（比如 MiniMax Code 网关，用 `x-api-key` 会直接返回 `401 token is required`）。

所以每个供应商可以单独指定：

```jsonc
{ "authStyle": "bearer" }   // 用 Authorization: Bearer
// 不写则默认 x-api-key（Anthropic）或 Bearer（OpenAI）
```

### 3. 降级链

链是一个**有序数组**，从上到下尝试：

```jsonc
"chain": [
  { "providerId": "provider-a", "modelId": "deepseek-chat", "enabled": true  },  // 首选
  { "providerId": "provider-b", "modelId": "claude-sonnet", "enabled": true  },  // 备胎
  { "providerId": "provider-c", "modelId": "glm-4",         "enabled": false }   // 禁用
]
```

**失败分类**（不同错误不同冷却时长；分类思路参考 workbuddy-openai-proxy / yuan240324, MIT）：

| 类型 | 触发条件 | 冷却 |
|---|---|---|
| `quota` | 402 / 额度不足 / 余额不足 / 积分不足 | 基础冷却 |
| `rate` | 429 / 限流 | **双倍**冷却 |
| `auth` | 401 / 403 / key 失效 | 基础冷却 |
| `network` | 连接超时 / DNS 失败 | 基础冷却 |
| `upstream` | 5xx | 基础冷却 |
| `bad_request` | 400（通常是请求本身有问题） | 不冷却，直接返回错误 |

失败后该节点进入冷却，链路自动往下走。冷却到期后**下一次请求会重试它**，成功则恢复。

### 4. 健康探测

除了被动失败，还有主动探测：每隔 `probeIntervalMs`（默认 5 分钟）对链上节点发一个极小的请求（`max_tokens: 8`），确认还活着。

这样即使没有真实流量，也能提前发现供应商挂了。

### 5. 账号池

> **设计来源说明**：账号池与「额度耗尽自动轮换」的设计，
> 参考了 [workbuddy-openai-proxy](https://github.com/yuan240324/workbuddy-openai-proxy)
> （作者 **yuan240324**，MIT License）。本项目为参照其思路的独立实现，未复制其源码。
> 详见 [CREDITS.md](../CREDITS.md)。

同一供应商可以有多个账号，请求时轮换：

```jsonc
{
  "id": "my-provider",
  "accounts": [
    { "id": "acc1", "key": "sk-xxx", "enabled": true },
    { "id": "acc2", "key": "sk-yyy", "enabled": true }
  ]
}
```

某个账号额度用尽或失效，会自动标记并跳到下一个。

## 配置文件完整说明

```jsonc
{
  "version": 1,
  "port": 8790,                    // 监听端口
  "host": "0.0.0.0",               // 监听地址
  "apiKey": "...",                 // 客户端连你时用的钥匙。留空会自动生成

  "exposeModel": "dafeiyu",        // 对外暴露的模型名，客户端只认这个
  "fallbackReply": "（稍后再试）",   // 全部失败时返回给客户端的话术

  "visionModel": {                 // 看图专用模型，不走降级链
    "providerId": "",              // 因为只有部分模型支持图片，需单独指定
    "modelId": "",
    "enabled": false
  },

  "providers": [
    {
      "id": "provider-a",          // 唯一标识，chain 里要用
      "label": "供应商A",           // 显示名
      "api": "openai",             // openai | anthropic
      "base": "https://api.a.com/v1",
      "key": "sk-xxx",
      "authStyle": "bearer",       // 可选：bearer | x-api-key
      "enabled": true,             // 整个供应商的开关
      "billingKind": "newapi",     // 决定额度查询方式：newapi | workbuddy | minimax | none
      "models": [
        {
          "id": "deepseek-chat",
          "name": "DeepSeek Chat",
          "enabled": true,         // 勾选才进降级链候选
          "contextWindow": 65536,
          "maxTokens": 4096
        }
      ],
      "accounts": []               // 可选：多账号轮换
    }
  ],

  "chain": [
    { "providerId": "provider-a", "modelId": "deepseek-chat", "enabled": true }
  ],

  "checkin": { "enabled": false }, // 自动签到总开关

  "failover": {
    "probeIntervalMs": 300000,     // 健康探测间隔（5 分钟）
    "cooldownMs": 120000,          // 失败后的基础冷却（2 分钟）
    "maxFailBeforeSkip": 1         // 连续失败几次才跳过
  }
}
```

## 对外接口

中转站**只实现 OpenAI 兼容接口**，因为这是事实标准。

| 路径 | 方法 | 说明 |
|---|---|---|
| `/v1/chat/completions` | POST | 对话，支持 `stream: true` |
| `/v1/models` | GET | 模型列表（只返回 `exposeModel`） |
| `/health` | GET | 健康检查 |
| `/` | GET | 管理面板（HTML） |

**调用示例：**

```bash
curl http://127.0.0.1:8790/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "dafeiyu",
    "messages": [{"role": "user", "content": "你好"}],
    "stream": true
  }'
```

注意 `model` 字段填什么都行 —— 中转站**不校验**，永远用 `exposeModel` 那条链。这样客户端换模型名也不会报错。

## 管理面板

打开 `http://你的IP:8790/` 就是管理面板，六个 Tab：

| Tab | 能干什么 |
|---|---|
| **概览** | 今日调用量、Token 消耗、失败数、7 天趋势、当前生效顺序 |
| **降级链** | 拖拽调顺序、启用/禁用节点、清空健康状态（解除冷却） |
| **供应商** | 增删改供应商，密钥单独管理（永不回显明文） |
| **模型** | 每个供应商的模型清单，勾选启用、设上下文长度 |
| **账号** | 账号池状态、额度、自动签到开关 |
| **接入** | 一键复制的 API Base / Key / 模型名，以及 curl 示例 |

面板用的 `apiKey` 由服务端注入到页面里，所以打开就能用，不需要手填。

## 环境变量

所有路径都可以用环境变量覆盖，方便部署到不同位置：

| 变量 | 默认 | 说明 |
|---|---|---|
| `RELAY_ROOT` | 当前工作目录 | 数据根目录 |
| `RELAY_CONFIG` | `$ROOT/relay.json` | 配置文件路径 |
| `RELAY_STATE` | `$ROOT/relay-state.json` | 运行态（健康、用量） |
| `RELAY_UI_DIR` | `$ROOT/ui` | 管理面板静态文件 |
| `RELAY_API_KEY` | 空（自动生成） | 初始 API Key |
| `PUBLIC_HOST` | `localhost` | 面板显示的对外地址 |
| `WB_PROXY` | `http://127.0.0.1:8788` | WorkBuddy 代理地址（可选功能） |
| `WB_PROXY_DIR` | 空 | WorkBuddy 代理目录（不填则该功能关闭） |
| `WB_SITES` | 空 | 账号池站点标识，逗号分隔 |

**不配置 WorkBuddy 相关变量时，账号池功能会自动跳过**，不影响主流程。

## 常见问题

**Q：一定要用它吗？我 AstrBot 直连不行吗？**

单供应商、不担心挂，确实不需要。但只要你接了 ≥2 家，或者被欠费/限流坑过一次，这个中间层就值回票价。

**Q：为什么不做成通用 OpenAI 网关（多用户、计费）？**

因为它是个人自用。加多租户、计费、配额，复杂度会翻好几倍，也没人用。保持单用户是刻意的取舍。

**Q：数据存哪？**

两个 JSON 文件：`relay.json`（配置）+ `relay-state.json`（健康状态和用量）。没有数据库，备份就是 `cp` 两个文件。

**Q：能水平扩展吗？**

不能，也没必要。单机几千 QPS 够个人用几辈子了。

**Q：为什么不用 TypeScript？**

因为要能 `node relay.mjs` 直接跑，不需要构建步骤。部署时省掉一个 `npm install` 和一次编译。
